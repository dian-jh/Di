# 文档编写与维护规范

> 本文档是 `docs/` 的维护准则。写文档、重组织文档、审查文档前先读这里。
> 根 `AGENTS.md`（由 `CLAUDE.md` 通过 `@AGENTS.md` 引入）的 `## Documentation` 一节是本文档的压缩版，细节以这里为准。

## 核心原则：文档是项目的一部分

`docs/` 与代码同等对待，不是一次性交付物。入口 `docs/README.md`（根索引），
核心模块文档在 `docs/modules/`。默认**每真实命名空间一篇**；模块文档长大到需拆分时，
退化为「每命名空间一个子目录 + 子 README + 多篇」（见 §叶子文档的拆分）。

## 索引结构：树形、轻量、按需生长

- 索引**树形分层、按需生长**：根索引（`docs/README.md`）→ 分类索引（如
  `docs/modules/README.md`）→ 文档。某个目录的文档增多或导航变复杂时，允许再拆子分类索引，
  **不设最大深度**，也不要求所有目录都有 README/索引，**不预先创建**没有实际价值的空目录、
  空索引与过深层级。层级由实际导航需求决定，而不是固定模板。
- 索引只做**导航**：每项一句话职责，指向具体文档；职责表 / 源码映射 / FAQ 等细节下沉到
  最近的子索引或文档本身，不在根索引重复。
- 查索引的 token 开销必须小于直接翻代码——任何单一索引保持在能一屏读完的量级。

### 各层职责（不与固定层级绑定）

- **根索引** `docs/README.md`：项目文档总入口；顶层文档一览 + 少量高频快速入口 + 全局导航规则。
  不枚举每个模块，不维护任何映射表。
- **分类索引**（如 `docs/modules/README.md`）：组织一个范围（模块集合 / 主题）；在该范围内导航，
  并在其作用域内承担唯一映射权威；提供子分类或（叶子）文档入口。
- **专题索引**：当某一机制 / 工作流 / 设计主题形成较大文档集合时，可建立独立专题索引。
  （例如极度膨胀后的架构专题、安全模型专题等。）
- **叶子文档**：保存有价值的知识并引用其它文档（链接或简短摘要），不再整体复制其它文档；
  过长时按「叶子文档的拆分」一拆多。

### 索引的渐进式扩展（何时拆分 / 何时保持扁平）

**考虑新增一个子分类索引**（→ `.../<分类>/README.md`）当下列条件**满足 ≥2 项**时。
这是软阈值，结合实际调整，不是硬性规定：

1. 父索引的直接条目较多——大致超过 10~14 条后，一次扫描的阅读成本明显上升。
2. 索引本身已接近一屏以上，读索引比读叶子文档更费时。
3. 条目已形成**可彼此独立**的多个子主题（各自成簇），且拆出的子分类能容纳 ≥2 篇文档。
4. 用户 / AI 常要扫过大量无关条目才能找到目标（导航精度下降）。
5. 更新索引容易遗漏或产生重复（增删高频、需反复重排）。
6. 增加一层能**降低端到端检索成本**——省下的每次扫描开销大于多一跳的导航开销。

**继续保持扁平**当：

- 条目少（大致 < 8）、主题单一、变动少。
- 拆出的子分类只能容纳 1 篇文档（"单文档索引" = 纯开销）。
- 文档尚未形成可分离的主题。
- 加一层不减少单跳扫描成本（无检索收益）。

深度**不设上限**，但只在同级条件再次满足时才继续生长；一个分类下只有一两篇文档时不该有
独立索引。拆分的实际改造步骤见「创建 / 移动 / 重命名 / 删除」。

### 叶子文档的拆分（一个命名空间何时一拆多）

上面讲的是**索引深度**（父索引条目多 → 拆子分类）。叶子文档自身的粒度是另一维：一篇模块文档
长到不可导航时，是拆成多篇，而不是继续加长单一文档。**拆分触发条件**（软阈值，≥2 项成立）：

1. 单篇叶子文档已超过一屏，通读成本超过「跳一跳 + 读局部」的成本。
2. 内部已形成 **≥2 个可独立检索**的子主题（如 `tools.md` 的「8 工具 / 注册表 / 共享基础设施 /
   说明注入 / 流动路径」）。
3. 读者常只需其中一小节，却被同一文件强制通读全文。

触发时：把该命名空间由单一 `xxx.md` 演进为子目录 `docs/modules/<模块>/`（子 `README.md` 做
模块内导航 + 多篇如 `architecture.md` / `workflow.md` / `troubleshooting.md`）。**在
`docs/modules/README.md` 权威表中仍只占一行**（指向子 `README.md` 而非具体叶子），表结构不变，
叶子数量不影响映射权威的形态。

**不拆分**当：单篇仍在一屏内、主题单一、读者基本都要通读（分篇反而增加跳转）。拆分的连带
更新义务同「创建 / 移动 / 重命名 / 删除」：子 README 建入口、更新父索引行、更新全部跨文档引用。

### 事实的唯一权威

下表是常见事实类别与唯一权威位置。其它文档若需提及某类事实，用链接或一句话摘要，
**不得复制完整表格、依赖图或长段内容**：

| 事实类别 | 唯一权威 |
|---|---|
| 模块 ↔ 文档 / 源码目录 / 测试目录 映射 | `docs/modules/README.md` |
| 跨模块依赖方向 + 一次数据流时序 | `docs/architecture.md` |
| 关键设计决策 | `docs/architecture.md` |
| CLI 契约（参数 / 模式 / headless / 换语言重写） | `docs/cli.md` |
| 家目录 `~/.di` 与分层配置规范 | `docs/di-home.md` |
| 功能全景 / MVP 缺口 / 工业级路线图 | `docs/roadmap.md` |
| 文档编写 / 组织 / 审查规范 | `docs/standards/documentation.md` |
| 项目文档总入口 + 导航规则 | `docs/README.md` |
| 面向用户的装 / 跑 / 配快速上手（含配置分层 / CLI 用法的用户视图） | 根 `README.md`（仓库根，不在 `docs/` 内） |

根索引不重复任何一张映射表 / 依赖图，它只是一个**路由器**。

根 `README.md` 面向人类用户，其配置 / CLI 用法应引用 `docs/di-home.md` / `docs/cli.md`，
或明确标注为对后者的用户视图摘录——**不重新定义事实**，同一事实的规范定义仍在 docs/ 内的
唯一权威处。

### 创建 / 移动 / 重命名 / 删除

做上述任何操作时，必须在**同一改动内**完成连带更新：

- **新建子分类索引**：创建 `.../<分类>/README.md`、搬入文档、在父索引加一行入口、
  更新所有指向被移动文档的跨文档引用。
- **移动 / 重命名 / 删除文档**：更新受影响模块文档、父索引、规范文档里的链接与路径。
- **新增模块 / 专题 / 文档**：先找最合适的既有索引位置（通常加一行 / 一段即可）；
  只有扩展触发条件成立才新建分类。不得为新事实建立多份互相独立的权威描述。
- **保持唯一权威**：若在某权威表加行，其它文档里本该删除的重复副本要一并删除。
- 不往长期文档里堆临时调试笔记、整段源码拷贝、无价值的实现日志。

## 1. 代码与文档一致

- 新增 / 修改 / 重命名 / 删除代码，或改变行为、接口、数据结构、调用图、架构时，
  检查相关文档并在**同一工作单元**内更新。
- 改动不影响任何现有文档时可以跳过——但要基于实际影响判断，不得默认跳过。
- 文档与源码冲突时，**信任源码、修正文档**。
- 不得留下与实现矛盾的文档；不得未核实实现就写文档。
- 描述实现的文档必须记录**仓库根相对源码路径**与**关键符号**（不得只写裸文件名，不带目录）；
  代码移动时同步更新。

## 2. 项目代码问题的查询流程

实现 / 行为 / 架构 / 调用链 / 调试类问题必须：

1. 先读 `docs/README.md`（或既定索引）。
2. 定位到具体功能文档——不得默认读全部 `docs/`。
3. 读文档中的相对源码路径与关键符号。
4. 打开真实源码核实实现。
5. 文档缺失 / 过时 / 不符时，核对必要相关代码后修正或补充文档。
6. 基于已核实的文档 + 代码作答。

纯语法、通用编程、或与本项目实现无关的问题，可直接作答，不必机械套用文档。

## 3. 按需读取、控制上下文开销

- 始终用渐进式策略：**索引 → 局部文档 → 必要源码**。
- 不为局部问题扫全部文档或整个代码库。
- 通过索引、明确相对路径、关键符号定位目标。跨文档引用使用**统一约定**：仓库根相对路径并带
  `docs/` 前缀（如 `docs/modules/llm.md`、`docs/cli.md`），不要在同一处混用裸文件名（`cli.md`）
  与 `docs/` 前缀（`docs/architecture.md`）。
- 仅在实际需要理解时，沿链路继续读依赖 / 调用方。
- 仅在下列情况扩大搜索：索引缺失、定位失败、问题跨模块、或需要完整审查。
- 不重复读取当前上下文中已完整且有效的信息。
- 不因省 token 而跳过核实、臆测行为、或忽略必要依赖。

## 4. 收尾前的文档一致性检查

实现 / 重构 / 修复缺陷后，检查：

- 是否需要新增或更新文档。
- 文档中的源码路径、类名、方法名是否仍有效。
- 文档中的调用图、行为描述、约束是否与实现一致。
- 功能目录 `README.md` 或顶层索引是否需要更新（含是否触发索引拆分 / 合并）。
- 本次改动是否破坏了任何文档链接或跨文档引用路径。

需要时在同一任务内更新文档；不需要时须确认文档确实不受影响——不得静默跳过检查。

## 5. 验证索引树与文档

完成文档改动后（尤其重组织时），做下列核对；发现问题，修复后重跑：

- 每个 `docs/` 跨文档引用路径都能解析到存在的文件；源码路径与测试路径存在。
- 所有正式文档都能从根索引沿索引树一步步找到（无权威文档成为"不可达孤岛"）。
- 索引没有引用不存在的文件；不保留空索引 / 空分类（无文档可索引）。
- 同一张映射表 / 依赖图 / 长段落没有出现在两个索引文件里（唯一权威未破坏）。
- 本次改动没有意外改到非文档文件（如 C# 源码）。
- 需要时运行 `dotnet test` 确认未破坏；若运行请如实记录是否执行与结果。
